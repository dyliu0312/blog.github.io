WSL Docker Configuration

WSL2 下 Docker 环境配置 (NVIDIA GPU 直通 · 文件权限 · 代理)

记录一次在 WSL2（原生 Docker，非 Docker Desktop）中让 Jellyfin 调用 NVIDIA GPU 转码的踩坑过程，顺带整理三项高频配置：NVIDIA Container Toolkit、WSL 挂载权限、Docker 走 systemd 代理。

一、背景

环境：Windows + WSL2（Ubuntu） + 原生安装的 Docker Engine（apt 版，非 Docker Desktop / Snap）。

目标：容器内能执行 nvidia-smi，并让 Jellyfin 使用 NVENC 硬件转码。

2.4 原理与注意点

  • WSL2 内核对 GPU 设备节点的 cgroups 白名单管理较严格，NVIDIA Runtime 默认依赖 cgroups 做设备授权会被拒绝。设为 false 后，运行时跳过 cgroups 限制，直接以设备节点方式注入 GPU。

  • 后续启动需要 GPU 的容器（如 Jellyfin）统一使用 --gpus all 这条已验证的路径，不要混用 CDI 的 --device nvidia.com/gpu=all。

  • 该配置写在配置文件里，WSL 重启一般保留；但 toolkit 升级时可能被覆盖重置，建议备份：

  • 排查过程中如有手动改过 /etc/cdi/nvidia.yaml，建议用 nvidia-ctk cdi generate 重新生成干净版本，并保持 mode = "auto" 即可，无需强制 "cdi"。

参数含义

选项 作用
metadata 允许在 Windows 挂载点保存 Linux 权限/owner 信息
umask=022 目录权限 → 755（默认 777 去掉 group/other 的写）
fmask=111 文件权限 → 去掉所有执行位（普通文件 → 644）

fmask=111 是解决 “Windows 下所有文件都可执行” 的关键，否则 git status 会刷屏，sh 也会误判脚本能否运行。

4.3 ⚠️ 关于 127.0.0.1 的注意点

代理运行在哪一侧，决定了地址该怎么写：

  • 代理运行在 WSL2 内部：127.0.0.1:7890 直接可用。
  • 代理运行在 Windows 宿主机（Clash / v2rayN 等）：WSL2 默认是 NAT 网络，127.0.0.1 指向 WSL2 自己，无法直连宿主代理。两种解法：

    1. 使用宿主 IP：http://$(ip route | awk '/default/ {print $3}'):7890，并确保代理软件开启 “允许局域网连接”；

    2. 在 Windows 端 %UserProfile%\.wslconfig 中启用镜像网络模式，让 127.0.0.1 直接映射到宿主：

      改完后 wsl --shutdown 再进入。

此外，容器内部访问宿主代理时，容器内的 127.0.0.1 也不是宿主，需要改写为宿主的 host.docker.internal 或网关 IP。
